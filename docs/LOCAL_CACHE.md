# Local browser storage

This document describes what the Deeperguard web client keeps on the device,
in which browser storage area, whether it is encrypted, and what happens at
sign-out and tab close. It was written by reading the client code in
`app/static/js/` and `app/static/sw.js` (and the inline boot script in
`app/templates/app.html`). Where the code does not settle a question, the
section says so.

**Short version:** note content and attachment bytes are stored in IndexedDB
as AES-GCM ciphertext. The vault key is derived in memory from your password
and is not written to storage. Some secrets are stored locally in a form that
is encrypted but whose decryption key sits next to the ciphertext in the same
browser origin. Notes are not expired by a timer: there is no offline lease or
TTL today (see [Cache lifetime](#cache-lifetime)).

## Storage inventory

### IndexedDB

Database name: `deeperguard` for the first account on a device, and
`deeperguard-<8-hex-hash-of-email>` for any further account
(`app/static/js/idb.js`, `dbName()`). The schema is version 2 with three object
stores:

| Store | Key | What it holds | Form |
| --- | --- | --- | --- |
| `items` | `uuid` | One row per note or folder/tag/view record: `ciphertext`, `content_hash`, `updated_at`, `deleted`, `has_blob`, `rev`. | **Ciphertext.** Written by `store.js` `persistLocal()` and sync paths via `wrapItem()` under the vault key. |
| `blobs` | `uuid` | Encrypted attachment bytes (`blob_ciphertext`). | **Ciphertext** (`store.js` `wrapped.blob_ciphertext`, `putBlob`). |
| `meta` | `key` | Sync bookkeeping: `lastSync`, the dirty-ID queue (`dirty`, a list of note UUIDs), the `freshness` payload, and the last upload-picker directory handle (`uploadPickerDir`). | Mixed. The dirty queue and `lastSync` are plaintext IDs and timestamps. The freshness payload was not checked for encryption (see [Uncertain](#where-the-behaviour-is-missing-or-uncertain)). |

The `idb.js` helper `iterateItems()` also copies a `content` field from a row
if one exists. The write paths I read never set it: every `putItem()` caller in
`store.js` writes `ciphertext`. I did not audit every caller, so treat "no
plaintext in IndexedDB" as what the code I read shows, not a guarantee.

### localStorage

Persists across tabs and restarts until cleared. Entries grouped by purpose:

**Secrets (encrypted, but the key is alongside them; see
[Device-remember](#device-remember-the-main-caveat)):**

- `notes_device_key`: raw 32-byte AES-GCM key, base64, generated by
  `vault-secrets.js` `getDeviceKey()`.
- `notes_device_password_enc`: the vault password, AES-GCM encrypted with
  `notes_device_key`. Written only when "remember this device" is on
  (`saveDevicePassword()`).
- `notes_device_password`: **legacy plaintext** copy of the vault password.
  `loadDevicePassword()` migrates it to the encrypted form on read, and every
  save path removes it. It is still read and cleared by sign-out.
- `notes_test_password`: read by the test-mode unlock path only (`app.js`
  `savedUnlockPassword()` when `skipLogin`). Removed on sign-out.

**Non-secret metadata and preferences (plaintext):**

- `deeperguard-prefs` (and legacy `homelab-notes-prefs`, migrated on read):
  UI and app preferences. `app.js` keeps vault-only settings out of this
  object on purpose ("API keys / OAuth tokens / app IDs never touch
  localStorage").
- `notes_email`: the signed-in account email, used to pick the IndexedDB name.
- `notes_idb_owner`: the account that owns the legacy `deeperguard` database.
- `notes_kdf_salt`, `notes_vault_kdf_version`, `notes_vault_kdf_upgrade_pending`,
  `notes_vault_kdf_migration_complete`: key-derivation parameters. A salt is
  public by design; it is not a key.
- `notes_device_id`: device identifier (`store.js`, `srp-auth.js`).
- `notes_device_phrase`: the anti-phishing phrase the user chose. Plaintext,
  and documented as never sent to the server (`device-phrase.js`). It survives
  sign-out on purpose.
- Timestamps and flags: `notes_offline_unlock_verified`,
  `notes_pwa_standalone_verified`, `notes_pinch_verified`,
  `notes_pending_device_report`, `notes_remember_device_declined`,
  `notes_offline_setup_dismissed`, `notes_offline_setup_modal_dismissed`,
  `notes_hero_guide_dismissed`, `notes_last_sync`, `notes_unfocused_at`,
  `notes_require_unlock_after_update`, `notes_require_typed_unlock`,
  `notes_freshness_test` (only set manually in a lab).
- `notes_sync_log` (`SYNC_LOG_KEY`): a sync diagnostic log. I did not check
  every field it records (see [Uncertain](#where-the-behaviour-is-missing-or-uncertain)).

### sessionStorage

Scoped to one tab. Cleared when the tab closes. Some entries survive a same-tab
reload, which is intended for the lock/unlock flow.

- `notes_csrf`: CSRF token for API calls.
- `notes_salt`, `notes_kdf_cache`: salt and a non-secret description of the
  last derived key (`store.js` ~line 478). The key itself is not stored there.
- `notes_unlocked`, `notes_unlock_at`, `notes_open_id`, `notes_app_tab`,
  `notes_totp_resync`, `notes_just_registered`, `notes_verify_email_hint`,
  `notes_update_dismissed_build`, `notes_pending_update_build`,
  `notes_user_requested_update`, `notes_allow_boot_unlock`,
  `notes_boot_password_ready`, `notes_deeplink_id` (`DEEP_LINK_KEY`): UI and
  flow state.
- Boot-unlock entries, used so a same-tab reload can unlock without retyping:
  - `notes_boot_key`: random 256-bit AES-GCM key, base64, generated per tab.
  - `notes_boot_password_enc`: the vault password, encrypted with
    `notes_boot_key`.
  - `notes_boot_kdf`: the derived Argon2 key bytes, encrypted with
    `notes_boot_key`, plus the salt and version.

  The boot key is in the same sessionStorage as its ciphertext, so the
  encryption protects against a casual copy of one field, not against a script
  running in the page. The boot entries are removed on consume, on clear, and
  on sign-out. They are cleared on lock too (`clearSecrets()`).

### Service worker Cache Storage

Defined in `app/static/sw.js`. Two caches, `deeperguard-offline` (versioned
assets and the crypto worker) and `deeperguard-shell` (the `/app` shell and
manifest).

- Cached: `/app`, `/manifest.json`, `/ca.crt`, the crypto vendor scripts
  (`noble-crypto.js`, `noble-argon2.js`, pdf.js), icons, and other
  same-origin `/static/` files via `cacheFirst`. Navigations to `/app` use
  `networkFirstNavigate`, which stores the last good `/app` HTML.
- Not cached: `/api/*`, the auth pages (`/login`, `/register`, `/totp`) and
  marketing pages are skipped by the fetch handler (`sw.js` ~line 437). Note
  content is never returned by the SW.
- The `/app` shell is HTML with script references. The code I read puts no
  note content into it. I did not check the rendered shell for user data.

### HTTP cache

Governed by server headers in `app/app.py`. `/sw.js` is
`max-age=0, must-revalidate`; `/app` and several API responses are
`no-store`. I checked the header setup in `app.py` (around lines 537-626) but
did not check every API route, so the claim that all API responses are
`no-store` is not verified.

## Ciphertext or plaintext

| Data | At rest |
| --- | --- |
| Note and folder/tag/view records (`items.ciphertext`) | AES-GCM ciphertext under the vault key |
| Attachment bytes (`blobs.blob_ciphertext`) | AES-GCM ciphertext |
| Vault password, "remember device" | AES-GCM ciphertext, but the key is in localStorage next to it (see below) |
| Vault password, legacy `notes_device_password` | Plaintext, until migrated or cleared |
| Boot-unlock password and derived key | AES-GCM ciphertext, with the key in the same sessionStorage |
| Preferences, email, salts, device phrase, timestamps | Plaintext |
| Vault key (derived from password) | Not stored. In memory only |

## Key material

- **The vault key is not persisted.** It is derived from the password and held
  in `state.cryptoKey` in memory. `NotesStore.lock()` (`store.js` ~line 846)
  zeroes the key bytes and clears `state.cryptoKey`, `lastDerivedKdf`, and
  `state.items`.
- **The in-memory KDF cache** (`lastDerivedKdf`) holds the derived key and the
  password for re-use within one session. It is zeroed on lock.
- **The derived key is also cached in sessionStorage**, but only encrypted
  under `notes_boot_key` (see the boot-unlock entries above).
- **Remember-device stores the vault password** (encrypted), not the derived
  key. Anyone who can read both `notes_device_key` and
  `notes_device_password_enc` from this origin can recover the password. The
  "encryption" is local obfuscation, not a second factor.

### Device-remember: the main caveat

When the "remember this device" preference is on, the vault password is kept
in localStorage in a form encrypted with `notes_device_key`, which is also in
localStorage. So the stored data is recoverable by anything that can read this
origin's localStorage: a same-origin script, a browser extension with page
access, or someone with the browser profile on disk. The encryption protects
against a casual read of one entry, not against anyone with the profile. A
hardware-bound or user-presence-bound key would be needed to change this, and
the code does not use one.

## Logout

The sign-out path is `signOutCompletely()` (`app/static/js/app.js` ~line 8175)
and then `clearLocalVaultAndLeave()` (~line 8107).

1. Flush pending writes (`NotesStore.flush()`).
2. Call `POST /api/auth/logout`. If that fails, the client still continues to
   step 3, so local data is cleared even when the server call fails.
3. `NotesStore.lock()`: zero the key bytes, clear in-memory items, remove
   `notes_unlocked` and `notes_kdf_cache` from sessionStorage.
4. `clearSavedUnlockSecrets()`: remove `notes_device_password`,
   `notes_test_password`, and calls `clearDevicePassword()`, which removes
   `notes_device_password_enc` and `notes_device_key`.
5. `NotesStore.clearDeviceData()` (`store.js` ~line 4013): clear the in-memory
   state and `NotesIDB.clearAll()` (the `items`, `blobs`, and `meta` stores),
   then remove sync and flag keys from localStorage (`notes_last_sync`,
   `notes_kdf_salt`, `notes_vault_kdf_*`, `notes_offline_unlock_verified`,
   `notes_pending_device_report`, `notes_remember_device_declined`,
   `notes_unfocused_at`, and the sync log). It also clears the session keys
   listed above and calls `NotesVaultSecrets.clearSecrets()`.
6. `localStorage.removeItem('notes_email')`, then redirect to `/login`.

**Kept on sign-out, on purpose:** `deeperguard-prefs`, `notes_device_id`,
`notes_device_phrase` and its dismissal flag, and the IndexedDB database
*name* mapping (`notes_idb_owner`, which is only consulted when the database
is opened). Service worker caches are not cleared by sign-out. They hold
app assets, not notes.

**Not verified:** whether every key listed above is removed on every sign-out
variant (for example the "session revoked" path, `wipeAfterRemoteSignOut`,
`app.js` ~line 8211). I read that path only to the point where it calls the
same wipe.

## Tab close, reload and lock

- **Tab close:** sessionStorage is discarded. IndexedDB, localStorage, and
  Cache Storage persist. Before the tab goes hidden or is unloaded, the client
  calls `NotesStore.flush()` (`visibilitychange`, `pagehide`, and
  `beforeunload` in `app.js` ~lines 23441 and 24342-24360). That is a best
  effort: the browser may kill the page first, so unsynced changes are kept in
  IndexedDB (`dirty` queue) and pushed on the next unlock.
- **Lock (idle, unfocus, manual):** `lockVault()` zeroes the key and clears
  in-memory items. It does **not** clear IndexedDB, localStorage, or the device
  remember entries. A locked device still has all ciphertext on disk, and the
  device-remember password, when enabled, still allows unlock without typing it.
- **Reload in the same tab:** sessionStorage survives, so the boot-unlock
  entries can unlock without retyping. Unsynced data is in IndexedDB and is
  not lost.

## Cache lifetime

**There is no offline lease or TTL.** I searched the client for `ttl`, `lease`,
`expire`, and max-age-style logic and found only session-expiry handling for
sign-in tokens, not for local data. Once synced, a note's ciphertext stays in
IndexedDB until it is deleted by the user, by sign-out, or by a sync prune of
tombstones. A device offline for 48 hours keeps its ciphertext, and with
remember-device enabled it can also unlock offline.

Idea #19 proposes a configurable TTL for the local note cache. It is not
implemented. Until it is, the honest answer to "how long is a note readable on
an offline device?" is: as long as the device stays unlocked-or-unlockable,
which with remember-device can be indefinitely. The proposed default is not
set in code and this document does not set one.

## What this does not protect

These are limits of the browser threat model, not bugs in one place.

- **A device with disk access.** Browser profiles are plain files. The
  ciphertext is useless without the password, but the remember-device password
  and its key are both in the profile, and the device-phrase and metadata are
  plaintext. An attacker with the profile can read the email, the device ID,
  and the preference set, and can recover the vault password when
  remember-device is on.
- **An offline or lost device.** Ciphertext stays on the device until sign-out
  or deletion, with no expiry (see above). A lost phone that was never signed
  out keeps the data on its flash storage, subject to the device's own
  encryption and lock screen.
- **Malicious browser extensions** with page or storage access can read
  localStorage, sessionStorage, and IndexedDB for this origin, and can read
  the key next to its ciphertext. They can also read the decrypted notes while
  the vault is unlocked, from the DOM.
- **A compromised browser or OS**, a same-origin XSS, or a supply-chain
  compromise of the served JavaScript can read keys in memory and the
  decrypted DOM. The CSP and the byte-stable service worker reduce but do not
  eliminate this.
- **Memory.** Zeroing key bytes on lock is best effort. JavaScript strings
  (for example the password once typed) are not zeroed, and the garbage
  collector may keep copies.
- **Attachment previews.** Decrypted attachment data may exist as object URLs
  or in memory while open. I did not check how long those persist.

## Where the behaviour is missing or uncertain

- **No TTL or offline lease.** Not implemented (idea #19 is a proposal).
- **Remember-device key co-location.** The device key is in the same origin's
  localStorage as its ciphertext. This is a design weakness documented here,
  not a planned fix.
- **Legacy `notes_device_password`.** Still readable as plaintext if present.
  It is migrated on read and cleared by sign-out, but a device that never
  signs in again keeps the plaintext copy.
- **The freshness payload** (`meta`, written in `freshness.js` ~line 907) was
  not checked for encryption.
- **The sync log** (`notes_sync_log`) content was not checked field by field.
- **Search index** (`NotesSearch`) was not checked for whether it stores
  plaintext outside memory.
- **The full sign-out variants** (session revoked, remote sign-out) were
  checked only to the point where they call the common wipe.
- **Service worker caches** were checked for note content by code reading
  only. No automated test verifies that the cache holds no user data.
- **Empirical verification** has not been done in a browser. Storage contents
  above come from reading the code, not from inspecting a running profile.

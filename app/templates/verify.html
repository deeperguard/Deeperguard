Independent check

Verify zero-knowledge

You do not have to trust our marketing copy. During sign-in and sync you can watch the real HTTP requests in your browser and confirm that passwords, vault keys, and note plaintext never appear on the wire.

1. Open DevTools Network

Chrome / Edge / Brave

  1. Open Sign in or the app in a normal (non-incognito) window if you already have an account.
  2. Press Ctrl+Shift+I (Windows/Linux) or ⌘+Option+I (macOS), or use the menu → More tools → Developer tools.
  3. Open the Network tab. Enable Preserve log so navigations do not clear the list.
  4. Filter by Fetch/XHR (or type api in the filter box).

Firefox

  1. Press Ctrl+Shift+E (Windows/Linux) or ⌘+Option+E (macOS), or menu → More tools → Web Developer Tools → Network.
  2. Enable Persist Logs. Filter to XHR / Fetch.

2. What to look for during login (SRP-6a)

Account sign-in uses Thinbus-compatible SRP-6a. The password is stretched in the browser (SHA-256 for legacy accounts, Argon2id for v2) and never posted as a field named password on the SRP routes.

  1. Reload /login, open Network, then sign in.
  2. Find POST /api/auth/srp/challenge. Request JSON is only {"email":"…"}. Response includes srp_salt, server public value B, and srp_kdf_version — not your password.
  3. Find POST /api/auth/srp/verify. Request JSON contains email, client public value A, and proof M1. Response includes server proof M2 plus vault metadata such as kdf_salt / vault_kdf_version for local unlock. There is still no password and no AES vault key.

Related proofs use the same shape: /api/auth/repair-login/challenge + /api/auth/repair-login (A/M1 only), and empty-vault unlock via /api/account/unlock/challenge + /api/account/unlock.

3. What to look for during sync

After unlock, create or edit a note and wait for sync (or pull to refresh). Filter Network for sync.

  • POST /api/sync/pull — body has cursors such as since, optional known_hashes, include_blobs, limit. Each returned item is ciphertext plus plaintext metadata only (see below).
  • POST /api/sync/items — push body is {"items":[…],"partial":1}. Each item carries item_uuid, ciphertext, optional blob_ciphertext, content_hash, deleted, updated_at, content_version, and often base_rev.
  • POST /api/sync/blobs / POST /api/sync/refetch — same ciphertext envelopes, still no note text.
  • GET /api/sync/item/<uuid> — the in-app “View server copy” action; returns one owned row exactly as stored.

The encrypted envelope is a JSON string (or object) with AES-GCM fields v, iv (base64 nonce), and data (base64 ciphertext). That is what leaves the device — not the note title or body.

Plaintext metadata the server can see without your vault password: item_uuid, content_version, content_hash, deleted, updated_at, synced_at, rev, and byte sizes of ciphertext fields. Account fields such as email live on the user row, not inside note ciphertext.

In the unlocked app, open any note → Note info → View server copy (also on files, 2FA entries, folders, and tags) to see the raw server JSON beside the decrypted local plaintext.

4. Optional: mitmproxy (and why Wireshark is not enough)

To inspect HTTPS as cleartext HTTP, point the browser at a local TLS-intercepting proxy such as mitmproxy, install its CA in the OS/browser trust store, and filter for deeperguard.com. You should still see only SRP proofs and ciphertext envelopes.

Wireshark on the wire without TLS keys shows only TLS records — encrypted blobs. That proves transport encryption, not that the application payload is ciphertext. Use DevTools or mitmproxy for application JSON.

What these tests can’t prove

  • Server-side retention of old copies — your browser only sees what the API returns now. Historical backups or DB snapshots are outside this check.
  • Metadata — email, IP address, request timing, ciphertext sizes, and item IDs are visible to the server and to anyone who can read logs or the database. Zero-knowledge covers vault contents, not traffic analysis.
  • Integrity of the delivered client code — if a compromised origin shipped a malicious app.js, it could exfiltrate secrets before encryption. Checking the code you run is a separate step.

Our claim fails if…

  • A login or sync request body contains your vault password, account password, or raw AES key material.
  • A sync item’s ciphertext / blob_ciphertext is readable plaintext (title, body, TOTP secret, file bytes) instead of a v/iv/data envelope.
  • Note contents appear in server access logs or error responses.
  • “View server copy” shows decrypted fields in the server JSON column (those belong only in the local plaintext column after unlock).

If you find any of the above, please email notes@deeperguard.com with subject “Vulnerability report”.

2. What to look for during login (SRP-6a)

Account sign-in uses Thinbus-compatible SRP-6a. The password is stretched in the browser (SHA-256 for legacy accounts, Argon2id for v2) and never posted as a field named password on the SRP routes.

  1. Reload /login, open Network, then sign in.
  2. Find POST /api/auth/srp/challenge. Request JSON is only {"email":"…"}. Response includes srp_salt, server public value B, and srp_kdf_version — not your password.
  3. Find POST /api/auth/srp/verify. Request JSON contains email, client public value A, and proof M1. Response includes server proof M2 plus vault metadata such as kdf_salt / vault_kdf_version for local unlock. There is still no password and no AES vault key.

Related proofs use the same shape: /api/auth/repair-login/challenge + /api/auth/repair-login (A/M1 only), and empty-vault unlock via /api/account/unlock/challenge + /api/account/unlock.

3. What to look for during sync

After unlock, create or edit a note and wait for sync (or pull to refresh). Filter Network for sync.

  • POST /api/sync/pull — body has cursors such as since, optional known_hashes, include_blobs, limit. Each returned item is ciphertext plus plaintext metadata only (see below).
  • POST /api/sync/items — push body is {"items":[…],"partial":1}. Each item carries item_uuid, ciphertext, optional blob_ciphertext, content_hash, deleted, updated_at, content_version, and often base_rev.
  • POST /api/sync/blobs / POST /api/sync/refetch — same ciphertext envelopes, still no note text.
  • GET /api/sync/item/<uuid> — the in-app “View server copy” action; returns one owned row exactly as stored.

The encrypted envelope is a JSON string (or object) with AES-GCM fields v, iv (base64 nonce), and data (base64 ciphertext). That is what leaves the device — not the note title or body.

Plaintext metadata the server can see without your vault password: item_uuid, content_version, content_hash, deleted, updated_at, synced_at, rev, and byte sizes of ciphertext fields. Account fields such as email live on the user row, not inside note ciphertext.

No new server-visible fields for sync freshness. Per-item version counters (__fv), bound item IDs (__fid), high-water marks, and the vault head chain live only inside AES-GCM ciphertext (or in vault-key-encrypted IndexedDB meta on the device). The server still sees only the same ciphertext envelope and existing metadata; it cannot read versions or tips.

In the unlocked app, open any note → Note info → View server copy (also on files, 2FA entries, folders, and tags) to see the raw server JSON beside the decrypted local plaintext.

4. Sync freshness (rollback / freeze / fork)

AES-GCM detects byte flips of ciphertext, but a server that only stores blobs could still serve an older valid ciphertext (rollback), withhold updates (freeze), or show different devices different histories (fork). Deeperguard clients detect those cases locally:

  • Per-item version — a monotonic __fv and the item’s UUID (__fid) sit inside the encrypted payload. Every real edit increments the version. The server cannot change them without breaking decryption.
  • High-water mark — each device stores (encrypted at rest) the highest version seen per item. A pull that offers a lower version is refused with: “The server returned an older version of this item.”
  • Vault head chain — an encrypted vault_head item holds a counter and a tip hash over sorted item_uuid:version pairs, chained to the previous tip. Settings → Signed-in devices shows this device’s counter and a short fingerprint for optional comparison.
  • Concurrent edits — two devices that advance from the same parent tip rebase to a merged tip without a fork alarm. A fork warning fires only when the same counter appears with tips that do not share a parent / chain link.
  • Device approval (out-of-band) — a trusted device can show an “Approve a new device” QR / short code / fingerprint built only from its local verified vault head (counter, tip hash, time). The new device records its first tip as Unverified start until that anchor matches (or the user skips). The server never supplies, signs, relays, or stores the anchor.

New device honesty: a brand-new device with no prior high-water marks adopts the first tip it downloads as Unverified start. It does not silently trust that tip. Confirm with a QR/code/fingerprint from a device you already trust (Settings → Signed-in devices), or skip and keep the Unverified start label. Matching counter+tip verifies; a higher local counter is accepted only when the chain links back to the anchor tip; a lower counter (or same counter with a different tip) shows a rollback/freeze/fork warning and does not verify.

Intentional restore: restoring an older backup asks for an explicit confirmation that resets high-water marks on this device so the older versions are accepted on purpose. After reset, the starting head is again Unverified until you re-approve (or, when the backup itself contains a vault_head, the restore can be labeled as anchored to that backup).

Reproducible checks (DevTools)

  1. Unlock the vault. In Console, run localStorage.setItem('notes_freshness_test','1') (required; the hooks do nothing without it).
  2. Pick a note UUID from NotesStore.state.items (or from Note info). A quiet sync alone often pulls items: 0, so the freshness check is never reached — use the end-to-end hook instead:
  1. That call raises the local high-water mark, re-fetches the item’s current server ciphertext via GET /api/sync/item/…, and runs it through the same applySyncPayload freshness gate used on normal pulls. It cannot disable crypto, export keys, or be triggered by the server.
  2. Byte-flip: in Application → IndexedDB (or via a lab sync fixture), flip one character inside a stored ciphertext data field and sync/reload. Decryption must fail; the item must not render as plaintext (integrity warning).

5. Secure Send (share / receive)

Secure Send encrypts a note (and optional file) in the browser, then stores only an opaque ciphertext blob on the server. The decryption key lives in the URL fragment (#…), which browsers never send to any server. An optional passphrase is stretched with the same client Argon2id parameters as vault KDF v2 and combined with a random fragment key so the link alone cannot decrypt.

  1. Open Secure Send from the sidebar (link icon) or Share by link on a note. Copy the full URL including the # part.
  2. Open DevTools → Network on the sender. POST /api/secure-send must contain only ciphertext (v/iv/data), expires_in, and max_views — never a filename, MIME type, passphrase, or fragment key.
  3. Open the receive URL in a private window with Network open. A plain GET or HEAD of /receive/<id> must not call /open (link-preview bots do not burn a view).
  4. Tap Open. POST /api/secure-send/<id>/open returns the same opaque ciphertext JSON. Response headers must not carry a real filename (Content-Disposition stays generic). File name, MIME, and size appear only after local decrypt.
  5. Confirm the receive scripts load with Subresource Integrity: secure-send.*.js and secure-send-receive.*.js (and their crypto dependencies) match the signed client manifest — the same SRI checks as the app shell.

6. Ask AI with Ollama Cloud

Ask AI is opt-in and is the one place note text can leave your vault in readable form.

  • Provider: Ollama Cloud at ollama.com. Your own API key is stored inside your encrypted vault.
  • What our server does: relays the request to ollama.com. It does not store your API key, the prompt, or the answer (same claim as Privacy / Settings).
  • What leaves your device: the text you choose to send for that request (title, body, and scanned text if enabled) — not the rest of your vault. Use the in-app send preview to see the exact payload.

7. Optional: mitmproxy (and why Wireshark is not enough)

To inspect HTTPS as cleartext HTTP, point the browser at a local TLS-intercepting proxy such as mitmproxy, install its CA in the OS/browser trust store, and filter for deeperguard.com. You should still see only SRP proofs and ciphertext envelopes.

Wireshark on the wire without TLS keys shows only TLS records — encrypted blobs. That proves transport encryption, not that the application payload is ciphertext. Use DevTools or mitmproxy for application JSON.

What these tests can’t prove

  • Server-side retention of old copies — your browser only sees what the API returns now. Historical backups or DB snapshots are outside this check. Client high-water marks detect a later rollback of an item this device already saw; they do not audit the server’s private history.
  • Pre-bootstrap history — without device approval, a brand-new device cannot prove the server did not already serve a rolled-back tip before that device existed. With Feature C, the out-of-band anchor comes from a device you already trust; that still cannot help if every device you own only ever saw the server’s rolled-back version, or if the “trusted” device itself is compromised.
  • Metadata — email, IP address, request timing, ciphertext sizes, and item IDs are visible to the server and to anyone who can read logs or the database. Zero-knowledge covers vault contents, not traffic analysis. Sync freshness adds no new plaintext metadata fields.
  • Integrity of the delivered client code — if a compromised origin shipped a malicious app.js, it could exfiltrate secrets before encryption or skip freshness checks. Checking the code you run is a separate step.
  • Colluding malicious clients — a device that willingly resets high-water marks (or never ran a current client) can accept older tips; compare fingerprints across devices you control.

How to check the code you’re running

After load, this page (and Settings → About) fetches same-origin assets listed in /static/client-manifest.json, hashes them in the browser (SubtleCrypto, canonical manifest_sha256 form), and compares that computed value to the manifest_sha256 published on the matching GitHub Release{% if release_tag %} {{ release_tag }}{% endif %} via the public GitHub Releases API (api.github.com). The expected value does not come from the Deeperguard server. The shell notes-client-hash meta is only a convenience mirror — if it differs from the computed hash, that is flagged. Outcomes: Matches signed release vX.Y.Z (optionally — newer release vA.B.C exists when the matched tag is older than /releases/latest), Does not match (only when a release hash was fetched and differs — no false alarms on network errors), or Could not check (offline / rate-limited / timed out, or naming any assets that could not be hashed). Loaded same-origin scripts/styles not listed in the manifest yield Does not match: unlisted asset …. The check never blocks the app and never sends note data.

Our claim fails if…

  • A login or sync request body contains your vault password, account password, or raw AES key material.
  • A sync item’s ciphertext / blob_ciphertext is readable plaintext (title, body, TOTP secret, file bytes) instead of a v/iv/data envelope.
  • Note contents appear in server access logs or error responses.
  • “View server copy” shows decrypted fields in the server JSON column (those belong only in the local plaintext column after unlock).

If you find any of the above, please email notes@deeperguard.com with subject “Vulnerability report”.
